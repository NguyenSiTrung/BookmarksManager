## Learnings from This Section

### Patterns Discovered
- **Consent for the decisions scope is direct Dexie** (`db.consents`, scope `jev_decisions`), read live via `useLiveQuery(() => hasConsent(...))`; a stale `consentVersion` row naturally re-displays the un-consented screen.
- **A `useLiveQuery` keyed on a changing arg retains the previous arg's result** across dep changes — emit `{arg, value}` and treat a mismatched `arg` as pending (the P4T1 stale-consent-flash fix).
- **One-shot effects must not close over changing state** — depend on a stable key and read current values from a ref, or keystrokes tear down the in-flight request (the P4T2 fix2).
- **Review-queue rows keyed by synthetic ids** (`popup:<uuid>`) must be filtered from actionable queues by namespace prefix, not by "unresolvable", so genuinely-deleted real bookmarks keep their Stale-but-approvable affordance.

### Gotchas Encountered
- `SAVE_SUGGEST` returns **counts only** — the UI must read `db.decisions` back; do not expect the suggestion payload in the message.
- Running the pipeline for a not-yet-saved bookmark under the user's real settings makes auto-apply target a nonexistent node (`apply_failed`) and hides the suggestion → save-suggest must suppress auto-apply.
- Radio-group `name` collisions across components on one page merge their inputs (`decisions-provider` vs `provider`).
- dexie-react-hooks **rethrows** observable errors, so `useLiveQuery` queriers must `.catch(...)`.
- **Rate limits interrupted four workers mid-task this section** — they left uncommitted work in their worktrees. Resuming a worker with its existing transcript (`run_subagent resume=<id>`) completed them cleanly.
